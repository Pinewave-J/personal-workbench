## 1. 五个必须先解决的冲突（都是读源码/配置实测，不是推测）

| # | 冲突 | 证据 | 影响 | 建议 |
|---|---|---|---|---|
| **C1** | **端口撞车：两边都用 8787** | 工作台后端 8787（HANDOFF 实测在跑）；KB agent `.env` `PORT=8787` | **两个服务无法同时运行** | KB agent 改 `PORT=8789`（8788 已被景观台账占用，8791 曾被测试实例用过） |
| **C2** | **KB agent 没有任何 CORS 头** | `server/index.js` 只设了 `nosniff` / `X-Frame-Options` / `Referrer-Policy`，**没有 `Access-Control-Allow-Origin`**，也没有 OPTIONS 处理器 | 工作台前端（由 DSH GUI `:3080` 提供）**无法在浏览器里直接 fetch 8789** | **必须由工作台 Express 后端代理**，前端不直连 KB agent |
| **C3** | **隐私口径相反** | KB agent 把检索到的片段发给 `api.deepseek.com` 与 `api.siliconflow.cn`；工作台 AI 通道的卖点是"**零 API key、数据不出本机**" | 混用会让"本机数据不出机器"的承诺**不再成立** | 见 D9：**默认只用本机的 `/api/search`（不出网）**，`/api/chat` 由用户显式触发 |
| **C4** | **问答只有 SSE，没有 JSON 版** | `POST /api/chat` 用 `text/event-stream`；无同步回答接口 | 工作台后端要拿"一句话答案"得消费 SSE | 用 `/api/search` 让 **DSH 当推理层**（见 §2.3），或给 KB agent 加一个非流式端点 |
| **C5** | **限流 30/min 对本地所有调用共用一个桶** | `RATE_LIMIT_PER_MIN=30`，按 `req.ip` 计数 | 批量检索/轮询会 429 | 工作台侧做缓存与合并；批量场景临时调高该值 |

### 另外两个工程差异（不影响架构，但写代码时会碰到）

- **模块系统不同**：工作台后端是 ESM（`"type":"module"`，`import`），KB agent 是 CommonJS（`require`）。互相拷贝代码要转换。
- **存储模型不同**：工作台是 SQLite + 事务；KB agent 是**整文件 JSON + 内存态**，且 `store.save()` 全量落盘。**绝不能让第二个进程直接写它的 `data/`**，只能走 HTTP 接口。

## 2. 推荐架构

### 2.1 关键判断：两者是**互补**的，不是竞争的

| | 个人工作台 | 知识库 Agent |
|---|---|---|
| 管什么 | **结构化字段**：项目/客户/任务/结果/日程 | **非结构化知识**：规范条文、历史标书、业绩材料 |
| 强项 | 状态机、编号、审计、金额归一、待办闭环 | 语义/关键词检索、引用溯源、防编造兜底 |
| 数据 | SQLite（可事务、可备份） | JSON 索引 + 向量二进制 |
| 出网 | **不出网**（DSH 当 AI） | 检索不出网；**问答出网** |

**分工一句话**：**工作台管「字段」，知识库管「知识」；DSH 当推理层，把两边合起来回答。**

### 2.2 目标架构

```
                  ┌─────────────────────────────────────┐
                  │  DSH Agent（推理层 · 零 key · 本机）  │
                  └─────────────────────────────────────┘
                     │                        │
      读知识（本机，不出网）          读业务数据（本机）
                     │                        │
                     ▼                        ▼
   ┌───────────────────────────┐   ┌───────────────────────────┐
   │ 知识问答 Agent  :8789      │   │ 个人工作台  :8787          │
   │  knowledge/ + uploads/     │   │  SQLite workbench.db       │
   │  POST /api/search ★        │   │  /api/v1/projects …        │
   │  POST /api/chat (SSE,出网) │   │  /api/v1/ai-jobs（暂存）    │
   └───────────────────────────┘   └───────────────────────────┘
                     ▲                        ▲
                     │   工作台后端代理        │
                     └────────────────────────┘
                        （前端不直连，规避 C2）
```

### 2.3 为什么把 `/api/search` 定为主接入点

KB agent 自己的 `/api/chat` 是"检索 + 模型作答"，会**出网、花额度、受 SSE 限制**。
而 `/api/search` **同步、JSON、不调模型、不出网**，返回带 `section` 与 `score` 的片段 —— 正好把"知识"喂给 DSH。
再把工作台的业务数据（项目/客户/任务）也交给 DSH，**推理与引用组织全部留在本机**：

```
用户：「某某新能源项目这个项目，投标保证金退还的规定在规范里是怎么写的？」
  DSH → 工作台 /api/v1/projects?q=某某新能源项目        → 拿到项目字段（PRJ-2026-019）
  DSH → 知识库 :8789 /api/search                  → 拿到规范条文片段 + section + 出处
  DSH → 综合回答，两处出处都标出来
```

**收益**：零代码改动即可跑通；保住"数据不出本机"；不消耗 API 额度；不受 SSE 阻碍。

### 2.4 三种结合模式（建议按此顺序推进）

| 模式 | 做法 | 代码改动 | 价值 |
|---|---|---|---|
| **① DSH 当枢纽**（**先做**） | DSH 同时调工作台 API 与 KB `/api/search`，回答时两边引用 | **零** | 当天可用；验证分工是否成立 |
| **② 工作台内嵌知识库** | 工作台后端加 `/api/v1/kb/*` 代理；前端「知识库」页放搜索框 + 命中列表 + 引用跳转 | 工作台（后端代理 + 前端页面） | 不切窗口就能查知识 |
| **③ 双向数据流** | 工作台上传招标文件/公告时自动进 KB；`kb_link` 把项目 ↔ 资料绑起来 | 工作台（迁移 + 前端）+ 可选 KB 小改 | 形成闭环 |

> **「知识库」页注意**：该导航项（id `kb`）2026-09-11 已被改成「系统图谱」。模式②要**恢复一个知识库页**，建议**新增独立导航项**而不是再抢 `kb`，避免又动一次图谱。

## 3. 关键契约（模式②③ 才需要）

### 3.1 join key

- 业务侧：**`project_code`（`PRJ-YYYY-NNN`）**，不用自增 id（恢复备份后 id 会变）。
- 知识侧：**`docId`**（16 位十六进制，= `文件名 + 内容哈希`，见 `loaders.makeDocId`）+ **`#ordinal`** 组成片段 id（如 `48ffe5d35a3a0c93#3`）。
- 引用串：`kb://<docId>#<ordinal>` → 工作台渲染成「打开《…》第 N 段」。

### 3.2 工作台侧新增（模式②）

```
GET  /api/v1/kb/proxy/search?q=…&topK=5      → 透传 KB /api/search，加本机缓存
GET  /api/v1/kb/proxy/stats                  → KB 资料清单与统计
POST /api/v1/kb/proxy/ingest-text            → 把公告原文推进 KB（可选）
GET  /api/v1/kb/links?entityType=&entityId=  → 业务记录 ↔ 资料
```

**代理必须做的四件事**：① 端口从配置读（不硬编码 8789）；② KB 未启动时返回"知识库未启动"而不是 500；③ 加本机缓存对抗 C5 限流；④ **不改 KB 的任何文件**，只走 HTTP。

### 3.3 回写契约（沿用既有铁律，不新造）

结构化抽取仍走现有 `ai_job` 队列；`ai.js` 的 `JOB_KIND` 若要扩，只加值：

```js
export const JOB_KIND = ["notice_extract", "kb_digest"];   // kb_digest 为候选，非必需
```

**铁律不变**：AI 只写 `ai_job` / `ai_suggestion`，落库一律人工确认 + 既有 `POST /projects`。
